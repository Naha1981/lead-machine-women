# PART 1: PRODUCT REQUIREMENTS DOCUMENT

## 1.1 Product Vision

**Lead Machine** is an AI-powered lead generation platform that gives every South African SME a professional website with an intelligent lead capture system. When a visitor fills the form, AI qualifies the lead instantly, sends a WhatsApp confirmation to the prospect, notifies the business owner, and logs everything in a simple dashboard.

**One sentence:** *Your business gets a website that turns visitors into paying clients while you sleep.*

---

## 1.2 Problem Statement

South African SMEs (law firms, consultants, coaches, recruiters, wellness brands) lose 70-80% of potential clients because:

1. They have no website or an outdated one
2. They respond to enquiries 24-48 hours later (or never)
3. They can't qualify leads — every enquiry gets the same treatment
4. They have no CRM — leads live in WhatsApp chats and memory
5. They can't afford a developer (R50K+) or a marketing agency (R15K/month)

**Lead Machine solves all 5 problems for R4,999/month.**

## 1.9 Database Design (Drizzle Schema)

```typescript
// packages/db/schema/organizations.ts
export const organizations = pgTable('organizations', {
  id: uuid('id').primaryKey().defaultRandom(),
  name: varchar('name', { length: 255 }).notNull(),
  slug: varchar('slug', { length: 100 }).unique().notNull(),
  industry: varchar('industry', { length: 100 }).notNull(),
  services: text('services'),                    // comma-separated
  logoUrl: varchar('logo_url', { length: 500 }),
  primaryColor: varchar('primary_color', { length: 7 }).default('#2563eb'),
  whatsappNumber: varchar('whatsapp_number', { length: 20 }),
  whatsappConnected: boolean('whatsapp_connected').default(false),
  evolutionInstanceId: varchar('evolution_instance_id', { length: 100 }),
  plan: varchar('plan', { length: 50 }).default('trial'),
  trialEndsAt: timestamp('trial_ends_at'),
  createdAt: timestamp('created_at').defaultNow(),
  updatedAt: timestamp('updated_at').defaultNow(),
});

// packages/db/schema/leads.ts
export const leads = pgTable('leads', {
  id: uuid('id').primaryKey().defaultRandom(),
  orgId: uuid('org_id').references(() => organizations.id).notNull(),
  name: varchar('name', { length: 255 }).notNull(),
  phone: varchar('phone', { length: 20 }).notNull(),
  email: varchar('email', { length: 255 }),
  serviceNeeded: varchar('service_needed', { length: 255 }),
  message: text('message'),
  source: varchar('source', { length: 50 }).default('website'),
  aiScore: integer('ai_score'),                 // 1-10
  aiTemperature: varchar('ai_temperature', { length: 10 }), // hot/warm/cold
  aiReason: text('ai_reason'),
  status: varchar('status', { length: 20 }).default('new'), // new/contacted/qualified/won/lost
  whatsappSent: boolean('whatsapp_sent').default(false),
  ownerNotified: boolean('owner_notified').default(false),
  consentGiven: boolean('consent_given').default(false),   // POPIA
  createdAt: timestamp('created_at').defaultNow(),
  updatedAt: timestamp('updated_at').defaultNow(),
});

// packages/db/schema/websites.ts
export const websites = pgTable('websites', {
  id: uuid('id').primaryKey().defaultRandom(),
  orgId: uuid('org_id').references(() => organizations.id).notNull(),
  template: varchar('template', { length: 50 }).notNull(),  // legal/consulting/wellness/construction/general
  heroHeadline: text('hero_headline'),
  heroSubtext: text('hero_subtext'),
  aboutText: text('about_text'),
  services: jsonb('services'),                  // [{name, description}]
  faq: jsonb('faq'),                            // [{question, answer}]
  customDomain: varchar('custom_domain', { length: 255 }),
  published: boolean('published').default(false),
  createdAt: timestamp('created_at').defaultNow(),
  updatedAt: timestamp('updated_at').defaultNow(),
});

// packages/db/schema/whatsapp-messages.ts
export const whatsappMessages = pgTable('whatsapp_messages', {
  id: uuid('id').primaryKey().defaultRandom(),
  orgId: uuid('org_id').references(() => organizations.id).notNull(),
  leadId: uuid('lead_id').references(() => leads.id),
  direction: varchar('direction', { length: 10 }).notNull(), // inbound/outbound
  phoneNumber: varchar('phone_number', { length: 20 }).notNull(),
  content: text('content').notNull(),
  messageType: varchar('message_type', { length: 20 }).default('text'),
  status: varchar('status', { length: 20 }).default('pending'), // pending/sent/delivered/read/failed
  evolutionMessageId: varchar('evolution_message_id', { length: 100 }),
  createdAt: timestamp('created_at').defaultNow(),
});

// packages/db/schema/subscriptions.ts
export const subscriptions = pgTable('subscriptions', {
  id: uuid('id').primaryKey().defaultRandom(),
  orgId: uuid('org_id').references(() => organizations.id).notNull(),
  paystackCustomerId: varchar('paystack_customer_id', { length: 100 }),
  paystackSubscriptionId: varchar('paystack_subscription_id', { length: 100 }),
  plan: varchar('plan', { length: 50 }).default('starter'),
  amountZar: integer('amount_zar').default(499900), // R4,999.00 in cents
  status: varchar('status', { length: 20 }).default('trial'), // trial/active/past_due/cancelled
  currentPeriodStart: timestamp('current_period_start'),
  currentPeriodEnd: timestamp('current_period_end'),
  cancelledAt: timestamp('cancelled_at'),
  createdAt: timestamp('created_at').defaultNow(),
});
```

## 1.11 AI Components

| Component | Model | Purpose | Prompt Strategy |
|-----------|-------|---------|-----------------|
| **Website Generator** | GPT-4o / Claude | Generate headline, about, services, FAQ from business profile | System prompt: "You are a conversion copywriter for SA SMEs..." |
| **Lead Qualifier** | GPT-4o-mini / Claude Haiku | Score lead 1-10, classify hot/warm/cold, give reason | Structured output (Zod schema): {score, temperature, reason, suggestedAction} |
| **WhatsApp Responder** | GPT-4o-mini | Reply to inbound WhatsApp messages using business FAQ | RAG from business FAQ + services. Tone matches brand. |
| **Chat Widget** | GPT-4o-mini (streaming) | Answer visitor questions on website, guide to form | System prompt with business context. CTA: "Fill the form and we'll WhatsApp you." |

## 1.13 User Flows

### Flow 1: Business Owner Signs Up
```
Sign Up (Clerk) → Create Org → Enter Business Details → Connect WhatsApp (QR scan)
→ AI Generates Website → Preview → Publish → Share Link → Start Getting Leads
```

### Flow 2: Visitor Becomes a Lead
```
Visitor lands on /s/[slug] → Fills form → Submits
→ API receives → AI qualifies (score + temperature) → Saves to DB
→ WhatsApp confirmation sent to visitor ("Thanks! MVR Law will call you within 2 hours.")
→ WhatsApp notification sent to owner ("🔥 NEW LEAD: Thabo M. | Score 9/10 | Contract review")
→ Lead appears in dashboard
```

### Flow 3: Owner Manages Leads
```
Owner opens dashboard → Sees leads sorted by score → Clicks "Hot" filter
→ Calls top lead → Updates status to "Contacted" → Eventually marks "Won"
→ Dashboard shows conversion metrics
```

## 2. Repository & Domain Architecture

Organize by **business capability**, never by technical layer.

```
src/

    (app)/                    # Authenticated app (dashboard, features)

    tenants/
    users/

    orders/
    payments/
    chat/

    search/

  shared/                     # Cross-domain utils, types, constants
```

### Module contract
Every module owns its: service functions (business logic), Zod validation schemas, database access, types, events emitted, and tests. Modules communicate via **exported service functions and events — never by reaching into each other's tables.**

### Layering rules
1. **Route Handlers are thin:** authenticate (Clerk `auth()`) → validate (Zod) → call service → return typed response. No business logic in handlers.
2. **Services are rich:** all business rules live in `modules/*/service.ts`, framework-agnostic, so extraction to a standalone service later is mechanical.
3. **UI never talks to integrations or the DB directly** — only through Route Handlers or Server Actions.
4. Prefer **Server Components** for reads, **Server Actions** for tightly coupled UI mutations, **REST Route Handlers** for anything external systems or multiple clients consume.

### The Single Authority Rule
> **From the trenches:** Multiple AI sessions created competing versions of the same homepage component, overwriting each other's fixes. The live site ended up with a Frankenstein of half-fixed copy.

**Every file has exactly one owner.** When an AI session creates or modifies a file, it must not create a *parallel* version of an existing component. If a component needs changing, **edit the existing file** — never create `Hero-v2.tsx` alongside `Hero.tsx`. If you're unsure whether a component already exists, **search first, create second.**

## 4. AI-First Architecture

Every application includes an AI layer as a first-class capability, using the **Vercel AI SDK** as the sole abstraction.

### Responsibilities
Conversation · reasoning · planning · classification · recommendations · semantic search · summarization · extraction · memory · tool calling · workflow orchestration.

### Iron rules
1. **Business rules never live in prompts.** Rules live in services; AI orchestrates services via tool calling.
2. **Grounded by construction:** every factual claim (prices, stock, balances, statuses) must originate from a tool call into application data. The model composes language; it never sources facts from weights.
3. **Provider-agnostic via Vercel AI SDK:** a single abstraction routes to OpenAI / Gemini / Claude / Groq / OpenRouter / Azure / Ollama. Switching providers or routing task classes to different models (cheap-fast vs. frontier) is configuration, not code. **Never import a provider SDK directly** — always go through `ai` from `@ai-sdk/*`.
4. **Tool registry:** tools are typed (Zod schemas), permission-checked per user/tenant, and audited.
5. **Memory tiers:** conversation (short-term) → user/customer profile (long-term, consented, deletable) → domain knowledge (RAG over pgvector).
6. **Evaluation gate:** maintain a golden-conversation test suite; score grounding accuracy, refusal correctness, and tone on every prompt/model change before deploy.
7. **Cost controls:** per-tenant token budgets, semantic caching, streaming responses by default.
8. **Prompt-injection defense:** user-supplied content (documents, images, messages) is data, never instructions.

### What you NEVER do with AI
- ❌ Use LangChain, LlamaIndex, or any other orchestration framework (Vercel AI SDK is the one)
- ❌ Import `openai`, `@google/generative-ai`, or `anthropic` directly in application code (go through the AI SDK)
- ❌ Put business logic in system prompts (put it in services; AI calls services via tools)
- ❌ Let the model source facts from its weights (always ground via tool calls)

## 5. Multi-Tenancy Standard

Default model: **shared database, `tenant_id` column on every business table, enforced at the data-access layer.**

- Every query helper requires a tenant context; raw unscoped queries are lint-blocked.
- Tenant isolation applies equally to: SQL queries, vector searches, AI tool calls, file storage paths, cache keys, and analytics.
- Automated cross-tenant leak tests run in CI. A leak is a Sev-1.
- Per-tenant database isolation is an enterprise upsell to design for, not a default to build.
- RBAC baseline: Owner / Admin / Member (+ domain roles as needed), enforced server-side via Clerk metadata or your own roles table. **Never trust the frontend.**

### Clerk + Multi-tenancy integration
- Clerk handles **identity** (who is this person?). Your app handles **tenancy** (which company do they belong to?).
- The `clerk_id` column on your `users` table is the bridge: Clerk `userId` → your `users.clerk_id` → `users.tenant_id` → tenant-scoped queries.
- Onboarding creates the tenant. All subsequent data access is scoped by `tenant_id`.
- Clerk Organizations (multi-tenancy) is **not** used by default — your app's own `tenants` table is simpler and gives you full control. Enable Clerk Organizations only if a project explicitly needs Clerk's built-in org management.

## 6. Integration Architecture

**Every external system connects through a dedicated integration client and terminates at a dedicated webhook route.** Never scatter SDK/HTTP calls through the application.

```
Client channels (Web · WhatsApp · Mobile · Slack · Email · API)
        ↓
Integration layer (src/lib/integrations/* — one typed client per provider)
        ↓
Webhook layer (app/api/webhooks/<provider> — verify → normalize → enqueue/dispatch)
        ↓
Application core (services + AI engine + events)
        ↓
Neon PostgreSQL → response back out through the same integration client
```

### Webhook rules (universal)
- Verify authenticity (signature/secret/source) **before** any processing.
- Normalize provider payloads into internal types at the boundary.
- Idempotency: dedupe by provider event ID; webhooks will be delivered twice.
- Persist the raw event before processing (audit + replay).
- Respond fast (2xx), do heavy work asynchronously.

### Evolution API (WhatsApp) standard
- One reusable Evolution client in `src/lib/integrations/evolution/`; never called from UI components.
- One Evolution instance per tenant; one shared webhook endpoint (`app/api/webhooks/evolution`) that routes by instance.
- Ignore bot-authored messages; log all inbound/outbound messages; normalize before business logic.
- Evolution runs on **Render free tier** with a **GitHub Actions wake-up cron** pinging `/wake` every 10 minutes to prevent sleep.
- WhatsApp is the **primary** messaging channel. Email is secondary and optional.

### Email standard (optional, provider-abstracted)
- Email lives behind a single client in `src/lib/integrations/email/` (or `brevo/`, `resend/`, `gmail/`).
- The notification service (`src/lib/notifications/`) calls the email client; it never imports a provider SDK directly.
- Swapping providers (Brevo → Resend → Gmail SMTP → SES) is a **one-file change** in the client. The rest of the app never knows.
- If no email provider is configured, `sendEmailSafe()` logs and returns null — **never crashes**.
- Email is **optional** for MVP. WhatsApp covers the critical alerts. Add email when revenue justifies it or when a client explicitly needs it.

### Payments standard
- Providers (PayFast, YOCO, Stripe) live behind a common payment abstraction in `src/lib/integrations/payments/`.
- **Browser redirects are never payment confirmation. Provider webhooks are the sole source of truth.** Verify signature, source, and amount before updating order state.
- Credentials exclusively from environment variables.

## 7. Data & Events

### Database design
- **Neon PostgreSQL is the single database.** No Supabase. No PlanetScale. No MongoDB. No Redis (unless a project explicitly justifies it).
- Single source of truth; never duplicate business state across systems.
- Canonical baseline schema (extend per domain): `tenants, users, roles, memberships, products, orders, customers, conversations, messages, documents, notifications, events, audit_logs, settings, integrations, ai_memory, embeddings`.
- Schema sync via `drizzle-kit push` (idempotent, simple, no migration files to manage). For production-critical schema changes, use `drizzle-kit generate` + `drizzle-kit migrate` for auditable migrations.
- Parameterized queries only. Never string-concatenate SQL.

### Event-driven design
Every significant business action emits a domain event (`OrderPlaced`, `PaymentConfirmed`, `MessageReceived`, `WorkflowCompleted`, ...), persisted to an `events` table.

Events power: analytics, attribution, notifications, AI memory, audit trails, and future integrations — and they are the seam along which services are later extracted.

### Search (layered, in order)
1. Postgres full-text search + filters
2. Semantic search (pgvector)
3. AI-assisted / hybrid re-ranked search

Users search naturally; keywords are a fallback, not the interface.

- REST by default; Server Actions for tightly coupled UI mutations.
- Validate **all** input with Zod at the boundary; infer types from schemas.
- Typed responses; structured error objects `{ error: { code, message, details? } }`; correct HTTP status codes.
- Version (`/api/v1/...`) only APIs consumed by external parties.

## 9. Security Baseline (non-negotiable, every project, every size)

- **Clerk handles authentication.** Your app handles authorization (tenant scoping, role checks) server-side via `auth()` from `@clerk/nextjs/server`.
- Tenant isolation (see §5) and per-query user scoping.
- Input validation (Zod) and output encoding everywhere.
- Secrets only in environment variables — never in code, never in the client bundle, never in GitHub.
- Webhook signature verification; HTTPS everywhere.
- Rate limiting; parameterized queries; audit logging of sensitive actions.
- Encryption in transit and at rest; PII minimization.
- Compliance posture appropriate to market (POPIA/GDPR): consent, purpose limitation, right to deletion (including AI memory and Clerk user data).
- **Clerk secret key (`sk_`) is server-only.** Never expose it in client code, never commit it, never log it.

## 10. Build Resilience

> **From the trenches:** CargoIQ's Vercel build went red for days because the code assumed environment variables were always present at build time. The local build passed (`.env` existed), but Vercel's build environment didn't have the vars, so the build crashed. Meanwhile, the developer kept pushing fixes that built green locally but red on Vercel, creating a growing pile of undeployed commits.

### Rule 1: The build must pass with ZERO environment variables
Every page, component, and module must be importable and buildable without any env vars present. This means:
- **Database clients are nullable:** `export const db = process.env.DATABASE_URL ? drizzle(neon(process.env.DATABASE_URL), { schema }) : null;`
- **Services guard against null db:** `if (!db) throw new Error('DATABASE_NOT_CONFIGURED');` at the top of any function that touches the database.
- **Auth-dependent pages use `export const dynamic = 'force-dynamic';`** so they're not statically pre-rendered at build time (which would trigger auth/db calls during the build).
- **API keys for external services are read at runtime, not at module load time.** Never call `new SomeClient(process.env.API_KEY!)` at the top level of a module. Read the key inside the function that uses it.

### Rule 2: Local green ≠ Vercel green
Always verify the Vercel deployment status after pushing. The Deployments tab is the source of truth, not your terminal. If the local build passes but Vercel's build fails, the error is in the Vercel build log — read it, don't guess.

### Rule 3: Test against production, not just localhost
Playwright E2E tests must run against the **live production URL** (via `BASE_URL=https://your-app.vercel.app`), not just `localhost:3000`. A test that passes locally but fails in production is a false green. The Playwright config should support both:
```ts
const baseURL = process.env.BASE_URL || 'http://localhost:3000';
const isLocal = baseURL.includes('localhost');
// Skip the local dev server when testing production:
...(isLocal ? { webServer: { command: 'npm run dev', url: baseURL, reuseExistingServer: true } } : {}),
```

### Rule 4: Graceful degradation over hard crashes
If an external service is unreachable, the app should log the error and continue — not crash. `sendEmailSafe()` returns null on failure. The Evolution webhook returns 200 even if the reply-send fails. The AI tool call catches errors and returns a structured failure the model can handle.

### Rule 5: The selftest pattern
Every critical pipeline (auth → data → notification → reply) gets a `/api/v1/selftest` endpoint that exercises the full flow with synthetic data and returns a structured result. This lets you verify the pipeline with a single `curl` command, without needing a real user, a real phone, or a real payment. Build it early. Use it often.

## 11. Vibe Coder Operating Rules

> These rules exist because you are building with AI coding assistants, and AI assistants have specific failure modes that a team of human engineers would naturally avoid. These rules compensate for those failure modes.

### Rule 1: One session, one scope
When you give an AI assistant a task, **scope it to one module or one concern.** Don't say "fix auth, redesign the homepage, and wire the WhatsApp webhook" in one prompt. Say "fix auth" → verify → "redesign the homepage" → verify → "wire the webhook." Each prompt should touch a bounded set of files. This prevents the AI from clobbering unrelated code.

### Rule 2: Search before you create
Before creating any new file, **search the repo for an existing file that does the same thing.** AI assistants love creating `Hero-v2.tsx` when `Hero.tsx` already exists. The instruction "read the existing code first, then edit it" should be in every prompt.

### Rule 3: Verify against production after every push
After every `git push`, check the Vercel Deployments tab. If the build is red, **stop and fix it before doing anything else.** A pile of undeployed commits is a time bomb. The live site is the truth; your local build is a suggestion.

### Rule 4: Don't build what you don't need yet (YAGNI for founders)
You don't need email if WhatsApp covers your alerts. You don't need a custom auth system if Clerk works. You don't need a vector database if Postgres full-text search handles your queries. You don't need a message queue if a cron job does the job. **Build the simplest thing that works for your next 10 users, not your imaginary 10,000.**

### Rule 5: Provider-abstract everything you might swap
Email provider, payment provider, AI model, WhatsApp instance — all behind typed clients in `src/lib/integrations/`. Swapping is a one-file change. This is the difference between "I'm locked in" and "I can switch in an afternoon."

### Rule 6: The dress rehearsal before the demo
Before showing anything to a real client or investor, **run the full flow end-to-end with real tools:** sign up on the live site, send a real WhatsApp message, check the live dashboard, open the proof page in an incognito window. The selftest endpoint (`/api/v1/selftest`) automates the backend check; the browser check catches what the API can't (broken buttons, wrong copy, missing pages).

### Rule 7: Commit early, commit often, commit explicitly
After every working change, commit with a descriptive message. Stage files explicitly (`git add src/app/login/page.tsx`), not blindly (`git add .`). This prevents half-finished work or secrets from being committed. If an AI session makes a mess, you can revert to the last good commit.

### Rule 8: The AI assistant is a junior developer, not a senior architect
AI assistants write plausible code that often has subtle bugs (wrong imports, missing null checks, incorrect API shapes, hardcoded values that should be configurable). **Review what the AI produces.** Run the tests. Check the live site. Don't trust the AI's "build passed" report without verifying it yourself. The AI is fast; you are the quality gate.

## 12. Testing

### Testing pyramid (progressive — start small, grow as revenue justifies)

**Day 1 (every project):**
- Playwright E2E on the critical path (sign up → log in → core feature → log out). **Run against production** (`BASE_URL=https://your-app.vercel.app`), not just localhost.
- The selftest endpoint (`/api/v1/selftest`) for backend pipeline verification.
- Manual browser check of the live site after every deploy (the "dress rehearsal").

**Week 1 (once the core flow works):**
- Unit tests on service functions (business logic) — the functions that compute money, enforce rules, or transform data.
- Integration tests on Route Handlers and webhooks (including idempotency and auth).

**Month 1 (once you have paying clients):**
- AI eval suite for prompts/tools (golden-conversation tests, grounding accuracy, refusal correctness).
- CI gates: typecheck, lint, tests, migration check on every PR. Preview deployment per PR.
- Cross-tenant leak tests.

**Quarter 1 (once you have 10+ clients):**
- Smoke E2E on every critical path, run in CI on every deploy.
- Observability: structured logs with request/tenant IDs, error tracking, key business metrics.
- Feature flags for risky launches; instant rollback via Vercel deployments.

### Playwright configuration standard
```ts
// playwright.config.ts
import { defineConfig } from '@playwright/test';

const baseURL = process.env.BASE_URL || 'http://localhost:3000';
const isLocal = baseURL.includes('localhost') || baseURL.includes('127.0.0.1');

export default defineConfig({
  testDir: './e2e',
  timeout: 30_000,
  expect: { timeout: 10_000 },
  fullyParallel: false,
  workers: 1,
  retries: process.env.CI ? 2 : 0,
  reporter: [['list'], ['html', { outputFolder: 'playwright-report', open: 'never' }]],
  use: {
    baseURL,
    viewport: { width: 1440, height: 900 },
    screenshot: 'on',
    trace: 'retain-on-failure',
  },
  ...(isLocal
    ? { webServer: { command: 'npm run dev', url: baseURL, reuseExistingServer: true, timeout: 120_000 } }
    : {}),
});
```

> **From the trenches:** The Playwright suite passed 9/9 "against production" — but it was actually hitting localhost because the `BASE_URL` env var wasn't picked up by the shell. The live site had completely different (broken) content. The lesson: **always verify which URL the tests are actually hitting**, and prefer running against the real production URL so you're testing what your users see.

## 13. Background Processing

Escalate only as workload proves need:

1. **Vercel Cron Jobs** — scheduled tasks (daily RLA checks, weekly summaries, monthly certificates).
2. **Triggered Route Handlers** — fire-and-forget with persistence (webhook processing, notification sending).
3. **Render workers (free tier)** — Playwright automation (portal scraping, PDF generation, heavy compute). Wake-up cron via GitHub Actions pinging `/wake` every 10 minutes.
4. **Durable workflows** (Vercel Workflow SDK) — multi-step, resumable orchestration (onboarding sequences, multi-day audit workflows).
5. **Message queues** — only when you have genuine throughput/ordering requirements that the above can't handle.

### Render worker standard
```
render-worker/
  package.json          # express, dotenv, playwright-core
  index.js              # /wake, /health, /api/v1/portals/* endpoints
```
- `/wake` returns `{"status":"AWAKE"}` — the GitHub Actions cron pings this every 10 minutes.
- `/health` returns service status, uptime, and capability flags.
- Portal automation endpoints use `playwright-core` with **lazy browser require** (the browser is only launched when a portal route is called, not at startup). If the browser isn't installed, the endpoint returns a structured error — **it never crashes the server.**
- The worker is a **separate package** with its own `package.json`. It is NOT part of the Next.js build. Vercel never touches it.

### GitHub Actions wake-up cron
```yaml
# .github/workflows/keep-render-warm.yml
name: Keep Render Warm
on:
  schedule:
    - cron: '*/10 * * * *'
  workflow_dispatch: {}
jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - name: Wake worker
        run: curl -sS -o /dev/null -w "worker=%{http_code}\n" "${{ secrets.WORKER_URL }}/wake" || true
      - name: Wake Evolution
        run: curl -sS -o /dev/null -w "evolution=%{http_code}\n" "${{ secrets.EVOLUTION_API_URL }}/" || true
```

## 15. Scalability & Extraction Playbook

Start with one deployable application. When **measured** production metrics show a bottleneck (latency, cost, team contention, compliance boundary), extract **only the affected module**:

1. The module already owns its logic, types, and data access (per §2) → move it behind its existing service interface.
2. Replace in-process calls with HTTP/queue calls at that interface.
3. Migrate its tables last, if ever.

Likely extraction candidates: AI engine, search, notifications, analytics pipeline, workflow engine, billing. **Never split pre-emptively.** You are one person. You will not need this for a long time. Design for it; don't build it.

## 16. Open-Source Integration & Architecture Preservation

> **The application owns the architecture. The open-source project never owns the application.**

Never restructure the application around a repository. Integrate the repository into the existing architecture (§2). The architecture is permanent; repositories are replaceable implementation details.

### Repository evaluation framework

| Type | Examples | Strategy |
|---|---|---|
| **1 — Utility** | Logger, date lib, PDF generator, CSV parser | Install directly. No wrapper unless it exposes business functionality. |
| **2 — Library / SDK** | AI SDK, OCR SDK, vector DB SDK | Install, then wrap behind an internal service. Never expose vendor APIs throughout the app. |
| **3 — Engine** | Recommendation, search, vision, workflow, RAG engines | Integrate through adapters behind domain services. Must remain replaceable. |
| **4 — Application** | CRM, ERP, booking system, CMS | **Never deploy as the product.** Extract valuable modules; rebuild inside your architecture. |
| **5 — Reference** | Demos, research prototypes | Study and borrow ideas. Never a production dependency. |

### Adapter pattern (mandatory for Types 2–4)
```
Business logic → internal service → adapter (src/lib/adapters/<repo>/) → repository
```
The application owns the interface; the repository provides the implementation. Swapping engines/repos is a configuration change, not a rewrite.

### Fork & upstream strategy
- Never ask "should I build my app inside this repository?" — ask "**which capabilities from this repository improve my app?**"
- Keep forks minimal and close to upstream. Never couple business logic to forked internals.

### Final test
Before any integration: *"Which capability does this add to my platform?"* — never *"How do I build my platform inside this repository?"*
