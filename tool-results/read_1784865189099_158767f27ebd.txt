    21→    21→## 1.1 Product Vision
    22→    22→
    23→    23→**Lead Machine** is an AI-powered lead generation platform that gives every South African SME a professional website with an intelligent lead capture system. When a visitor fills the form, AI qualifies the lead instantly, sends a WhatsApp confirmation to the prospect, notifies the business owner, and logs everything in a simple dashboard.
    24→    24→
    25→    25→**One sentence:** *Your business gets a website that turns visitors into paying clients while you sleep.*
    26→    26→

    29→    29→## 1.2 Problem Statement
    30→    30→
    31→    31→South African SMEs (law firms, consultants, coaches, recruiters, wellness brands) lose 70-80% of potential clients because:
    32→    32→
    33→    33→1. They have no website or an outdated one
    34→    34→2. They respond to enquiries 24-48 hours later (or never)
    35→    35→3. They can't qualify leads — every enquiry gets the same treatment
    36→    36→4. They have no CRM — leads live in WhatsApp chats and memory
    37→    37→5. They can't afford a developer (R50K+) or a marketing agency (R15K/month)
    38→    38→
    39→    39→**Lead Machine solves all 5 problems for R4,999/month.**

   728→   728→## 1. The Stack — One Choice Per Layer, No Alternatives
   729→   729→
   730→   730→Every project uses this exact stack. No "or Prisma if justified." No "or Auth.js." No "or Supabase." One tool per job. Fewer decisions = fewer mistakes.
   731→   731→
   732→   732→| Layer | The One Choice | Why This One |
   733→   733→|---|---|---|
   734→   734→| **Framework** | Next.js (latest, App Router) + TypeScript (strict) | Frontend AND backend in one repo. One `npm run build`. One deploy. |
   735→   735→| **UI** | Tailwind CSS + shadcn/ui | Design tokens, no ad-hoc colors, consistent look across all your apps. |
   736→   736→| **Forms / Validation** | React Hook Form + Zod | Zod schemas shared client/server. One schema, two uses. |
   737→   737→| **Client data fetching** | TanStack Query | Never fetch in `useEffect`. Cache, retry, and loading states for free. |
   738→   738→| **Client state** | Zustand — only when server state isn't enough | Prefer server state. Add Zustand only for genuinely client-only state. |
   739→   739→| **Database** | Neon PostgreSQL | Serverless, free tier, connection pooling, pgvector-ready. One database for everything. |
   740→   740→| **ORM** | Drizzle ORM + `drizzle-kit push` | Typed queries, simple idempotent schema sync. No migration files to manage manually. |
   741→   741→| **Auth** | **Clerk** (and nothing else) | Prebuilt sign-in/up, session management, middleware gating, free for 10k MAU. Zero custom auth code. Ever. |
   742→   742→| **AI** | Vercel AI SDK | Provider-agnostic (OpenAI, Gemini, Claude, Groq, etc.), streaming, tool calling. One SDK, any model. |
   743→   743→| **File storage** | Vercel Blob | Managed, no infra, no S3 buckets to configure. |
   744→   744→| **Payments** | PayFast / Stripe behind a common abstraction | Webhooks are payment truth. Browser redirects are never confirmation. |
   745→   745→| **WhatsApp** | Evolution API (self-hosted on Render, free tier) | One instance per tenant. Webhook-first. Free. |
   746→   746→| **Email** | Provider-abstracted client (optional) | Resend, Gmail SMTP, or SES — swap one file. Email is secondary; WhatsApp is primary. |
   747→   747→| **Deployment** | Vercel | Serverless, preview deploys per PR, free tier, edge network. |
   748→   748→| **Background workers** | Render (free tier) | Playwright automation, portal scraping, heavy compute. Wake-up cron via GitHub Actions. |
   749→   749→| **E2E testing** | Playwright | Real browser, real clicks, real assertions. **Run against production, not just localhost.** |
   750→   750→| **Version control** | GitHub | One repo per app. GitHub Actions for crons and CI. |
   751→   751→
   752→   752→**Never** create a separate FastAPI / Express / NestJS / Django backend. **Never** use a different database. **Never** use a different auth provider. **Never** use a different deployment target. The stack is the stack.

Clerk ended that in one afternoon. The lesson: **pick the managed, prebuilt, "it just works" option every time.** You are not building auth. You are building a business.

   799→   799→Every module owns its: service functions (business logic), Zod validation schemas, database access, types, events emitted, and tests. Modules communicate via **exported service functions and events — never by reaching into each other's tables.**
   800→   800→
   801→   801→### Layering rules
   802→   802→1. **Route Handlers are thin:** authenticate (Clerk `auth()`) → validate (Zod) → call service → return typed response. No business logic in handlers.

   808→   808→> **From the trenches:** Multiple AI sessions created competing versions of the same homepage component, overwriting each other's fixes. The live site ended up with a Frankenstein of half-fixed copy.
   809→   809→

If a component needs changing, **edit the existing file** — never create `Hero-v2.tsx` alongside `Hero.tsx`. If you're unsure whether a component already exists, **search first, create second.**

   819→   819→- Prebuilt sign-in / sign-up / user-management UI components that look professional out of the box and are themeable to your design system.
   820→   820→- Session management, cookie handling, edge-runtime compatibility, and middleware gating — all handled by Clerk, not by you.
   821→   821→- Free for 10,000 monthly active users. No credit card.
   822→   822→- First-class Next.js App Router support. Works natively on Vercel.
   823→   823→- Eliminates the entire class of "auth is broken" bugs that plague hand-rolled systems.
   824→   824→
   825→   825→### Clerk integration pattern (every project)
   826→   826→
   827→   827→**1. Install:**

   872→   872→export const config = {

   920→   920→- If the user already has a tenant, `/onboarding` redirects straight to `/dashboard`.

   930→   930→### What you NEVER do with auth
   931→   931→- ❌ Write your own password hashing (scrypt, bcrypt, argon2)
   932→   932→- ❌ Create your own session table or cookie management
   933→   933→- ❌ Use Better Auth, Auth.js, NextAuth, Supabase Auth, Firebase Auth, or any other auth library
   934→   934→- ❌ Build custom sign-in / sign-up forms (use Clerk's `<SignIn />` and `<SignUp />`)
   935→   935→- ❌ Store passwords in your database (Clerk handles credential storage)
   936→   936→- ❌ Trust client-side auth state for authorization (always verify server-side via `auth()`)

The custom scrypt system had a dead sign-in button, a missing sign-in endpoint, and a signup route that called a library against database tables that didn't exist. Clerk ended all of it in one afternoon. **Never build auth. Rent it.**

   942→   942→## 4. AI-First Architecture
   943→   943→
   944→   944→Every application includes an AI layer as a first-class capability, using the **Vercel AI SDK** as the sole abstraction.
   945→   945→
   946→   946→### Responsibilities
   947→   947→Conversation · reasoning · planning · classification · recommendations · semantic search · summarization · extraction · memory · tool calling · workflow orchestration.
   948→   948→
   949→   949→### Iron rules
   950→   950→1. **Business rules never live in prompts.** Rules live in services; AI orchestrates services via tool calling.
   951→   951→2. **Grounded by construction:** every factual claim (prices, stock, balances, statuses) must originate from a tool call into application data. The model composes language; it never sources facts from weights.
   952→   952→3. **Provider-agnostic via Vercel AI SDK:** a single abstraction routes to OpenAI / Gemini / Claude / Groq / OpenRouter / Azure / Ollama. Switching providers or routing task classes to different models (cheap-fast vs. frontier) is configuration, not code. **Never import a provider SDK directly** — always go through `ai` from `@ai-sdk/*`.
   953→   953→4. **Tool registry:** tools are typed (Zod schemas), permission-checked per user/tenant, and audited.
   954→   954→5. **Memory tiers:** conversation (short-term) → user/customer profile (long-term, consented, deletable) → domain knowledge (RAG over pgvector).
   955→   955→6. **Evaluation gate:** maintain a golden-conversation test suite; score grounding accuracy, refusal correctness, and tone on every prompt/model change before deploy.
   956→   956→7. **Cost controls:** per-tenant token budgets, semantic caching, streaming responses by default.
   957→   957→8. **Prompt-injection defense:** user-supplied content (documents, images, messages) is data, never instructions.
   958→   958→
   959→   959→### What you NEVER do with AI
   960→   960→- ❌ Use LangChain, LlamaIndex, or any other orchestration framework (Vercel AI SDK is the one)
   961→   961→- ❌ Import `openai`, `@google/generative-ai`, or `anthropic` directly in application code (go through the AI SDK)
   962→   962→- ❌ Put business logic in system prompts (put it in services; AI calls services via tools)
   963→   963→- ❌ Let the model source facts from its weights (always ground via tool calls)

   967→   967→## 5. Multi-Tenancy Standard
   968→   968→
   969→   969→Default model: **shared database, `tenant_id` column on every business table, enforced at the data-access layer.**
   970→   970→
   971→   971→- Every query helper requires a tenant context; raw unscoped queries are lint-blocked.
   972→   972→- Tenant isolation applies equally to: SQL queries, vector searches, AI tool calls, file storage paths, cache keys, and analytics.
   973→   973→- Automated cross-tenant leak tests run in CI. A leak is a Sev-1.
   974→   974→- Per-tenant database isolation is an enterprise upsell to design for, not a default to build.
   975→   975→- RBAC baseline: Owner / Admin / Member (+ domain roles as needed), enforced server-side via Clerk metadata or your own roles table. **Never trust the frontend.**
   976→   976→
   977→   977→### Clerk + Multi-tenancy integration
   978→   978→- Clerk handles **identity** (who is this person?). Your app handles **tenancy** (which company do they belong to?).
   979→   979→- The `clerk_id` column on your `users` table is the bridge: Clerk `userId` → your `users.clerk_id` → `users.tenant_id` → tenant-scoped queries.
   980→   980→- Onboarding creates the tenant. All subsequent data access is scoped by `tenant_id`.
   981→   981→- Clerk Organizations (multi-tenancy) is **not** used by default — your app's own `tenants` table is simpler and gives you full control. Enable Clerk Organizations only if a project explicitly needs Clerk's built-in org management.

   985→   985→## 6. Integration Architecture
   986→   986→
   987→   987→**Every external system connects through a dedicated integration client and terminates at a dedicated webhook route.** Never scatter SDK/HTTP calls through the application.
   988→   988→
   989→   989→```
   990→   990→Client channels (Web · WhatsApp · Mobile · Slack · Email · API)
   991→   991→        ↓
   992→   992→Integration layer (src/lib/integrations/* — one typed client per provider)
   993→   993→        ↓
   994→   994→Webhook layer (app/api/webhooks/<provider> — verify → normalize → enqueue/dispatch)
   995→   995→        ↓
   996→   996→Application core (services + AI engine + events)
   997→   997→        ↓
   998→   998→Neon PostgreSQL → response back out through the same integration client
   999→   999→```
  1000→  1000→
  1001→  1001→### Webhook rules (universal)
  1002→  1002→- Verify authenticity (signature/secret/source) **before** any processing.
  1003→  1003→- Normalize provider payloads into internal types at the boundary.
  1004→  1004→- Idempotency: dedupe by provider event ID; webhooks will be delivered twice.
  1005→  1005→- Persist the raw event before processing (audit + replay).
  1006→  1006→- Respond fast (2xx), do heavy work asynchronously.
  1007→  1007→
  1008→  1008→### Evolution API (WhatsApp) standard
  1009→  1009→- One reusable Evolution client in `src/lib/integrations/evolution/`; never called from UI components.
  1010→  1010→- One Evolution instance per tenant; one shared webhook endpoint (`app/api/webhooks/evolution`) that routes by instance.
  1011→  1011→- Ignore bot-authored messages; log all inbound/outbound messages; normalize before business logic.
  1012→  1012→- Evolution runs on **Render free tier** with a **GitHub Actions wake-up cron** pinging `/wake` every 10 minutes to prevent sleep.
  1013→  1013→- WhatsApp is the **primary** messaging channel. Email is secondary and optional.
  1014→  1014→
  1015→  1015→### Email standard (optional, provider-abstracted)
  1016→  1016→- Email lives behind a single client in `src/lib/integrations/email/` (or `brevo/`, `resend/`, `gmail/`).
  1017→  1017→- The notification service (`src/lib/notifications/`) calls the email client; it never imports a provider SDK directly.
  1018→  1018→- Swapping providers (Brevo → Resend → Gmail SMTP → SES) is a **one-file change** in the client. The rest of the app never knows.
  1019→  1019→- If no email provider is configured, `sendEmailSafe()` logs and returns null — **never crashes**.
  1020→  1020→- Email is **optional** for MVP. WhatsApp covers the critical alerts. Add email when revenue justifies it or when a client explicitly needs it.
  1021→  1021→
  1022→  1022→### Payments standard
  1023→  1023→- Providers (PayFast, YOCO, Stripe) live behind a common payment abstraction in `src/lib/integrations/payments/`.
  1024→  1024→- **Browser redirects are never payment confirmation. Provider webhooks are the sole source of truth.** Verify signature, source, and amount before updating order state.
  1025→  1025→- Credentials exclusively from environment variables.

  1029→  1029→## 7. Data & Events
  1030→  1030→
  1031→  1031→### Database design
  1032→  1032→- **Neon PostgreSQL is the single database.** No Supabase. No PlanetScale. No MongoDB. No Redis (unless a project explicitly justifies it).
  1033→  1033→- Single source of truth; never duplicate business state across systems.
  1034→  1034→- Canonical baseline schema (extend per domain): `tenants, users, roles, memberships, products, orders, customers, conversations, messages, documents, notifications, events, audit_logs, settings, integrations, ai_memory, embeddings`.
  1035→  1035→- Schema sync via `drizzle-kit push` (idempotent, simple, no migration files to manage). For production-critical schema changes, use `drizzle-kit generate` + `drizzle-kit migrate` for auditable migrations.
  1036→  1036→- Parameterized queries only. Never string-concatenate SQL.
  1037→  1037→
  1038→  1038→### Event-driven design
  1039→  1039→Every significant business action emits a domain event (`OrderPlaced`, `PaymentConfirmed`, `MessageReceived`, `WorkflowCompleted`, ...), persisted to an `events` table.
  1040→  1040→
  1041→  1041→Events power: analytics, attribution, notifications, AI memory, audit trails, and future integrations — and they are the seam along which services are later extracted.
  1042→  1042→
  1043→  1043→### Search (layered, in order)
  1044→  1044→1. Postgres full-text search + filters
  1045→  1045→2. Semantic search (pgvector)
  1046→  1046→3. AI-assisted / hybrid re-ranked search
  1047→  1047→
  1048→  1048→Users search naturally; keywords are a fallback, not the interface.

  1079→  1079→## 10. Build Resilience
  1080→  1080→
  1081→  1081→> **From the trenches:** CargoIQ's Vercel build went red for days because the code assumed environment variables were always present at build time. The local build passed (`.env` existed), but Vercel's build environment didn't have the vars, so the build crashed. Meanwhile, the developer kept pushing fixes that built green locally but red on Vercel, creating a growing pile of undeployed commits.
  1082→  1082→
  1083→  1083→### Rule 1: The build must pass with ZERO environment variables
  1084→  1084→Every page, component, and module must be importable and buildable without any env vars present. This means:
  1085→  1085→- **Database clients are nullable:** `export const db = process.env.DATABASE_URL ? drizzle(neon(process.env.DATABASE_URL), { schema }) : null;`
  1086→  1086→- **Services guard against null db:** `if (!db) throw new Error('DATABASE_NOT_CONFIGURED');` at the top of any function that touches the database.
  1087→  1087→- **Auth-dependent pages use `export const dynamic = 'force-dynamic';`** so they're not statically pre-rendered at build time (which would trigger auth/db calls during the build).
  1088→  1088→- **API keys for external services are read at runtime, not at module load time.** Never call `new SomeClient(process.env.API_KEY!)` at the top level of a module. Read the key inside the function that uses it.
  1089→  1089→
  1090→  1090→### Rule 2: Local green ≠ Vercel green
  1091→  1091→Always verify the Vercel deployment status after pushing. The Deployments tab is the source of truth, not your terminal. If the local build passes but Vercel's build fails, the error is in the Vercel build log — read it, don't guess.
  1092→  1092→
  1093→  1093→### Rule 3: Test against production, not just localhost
  1094→  1094→Playwright E2E tests must run against the **live production URL** (via `BASE_URL=https://your-app.vercel.app`), not just `localhost:3000`. A test that passes locally but fails in production is a false green. The Playwright config should support both:
  1095→  1095→```ts
  1096→  1096→const baseURL = process.env.BASE_URL || 'http://localhost:3000';
  1097→  1097→const isLocal = baseURL.includes('localhost');
  1098→  1098→// Skip the local dev server when testing production:
  1099→  1099→...(isLocal ? { webServer: { command: 'npm run dev', url: baseURL, reuseExistingServer: true } } : {}),
  1100→  1100→```
  1101→  1101→
  1102→  1102→### Rule 4: Graceful degradation over hard crashes
  1103→  1103→If an external service is unreachable, the app should log the error and continue — not crash. `sendEmailSafe()` returns null on failure. The Evolution webhook returns 200 even if the reply-send fails. The AI tool call catches errors and returns a structured failure the model can handle.
  1104→  1104→
  1105→  1105→### Rule 5: The selftest pattern
  1106→  1106→Every critical pipeline (auth → data → notification → reply) gets a `/api/v1/selftest` endpoint that exercises the full flow with synthetic data and returns a structured result. This lets you verify the pipeline with a single `curl` command, without needing a real user, a real phone, or a real payment. Build it early. Use it often.

  1110→  1110→## 11. Vibe Coder Operating Rules
  1111→  1111→
  1112→  1112→> These rules exist because you are building with AI coding assistants, and AI assistants have specific failure modes that a team of human engineers would naturally avoid. These rules compensate for those failure modes.
  1113→  1113→
  1114→  1114→### Rule 1: One session, one scope
  1115→  1115→When you give an AI assistant a task, **scope it to one module or one concern.** Don't say "fix auth, redesign the homepage, and wire the WhatsApp webhook" in one prompt. Say "fix auth" → verify → "redesign the homepage" → verify → "wire the webhook." Each prompt should touch a bounded set of files. This prevents the AI from clobbering unrelated code.
  1116→  1116→
  1117→  1117→### Rule 2: Search before you create
  1118→  1118→Before creating any new file, **search the repo for an existing file that does the same thing.** AI assistants love creating `Hero-v2.tsx` when `Hero.tsx` already exists. The instruction "read the existing code first, then edit it" should be in every prompt.
  1119→  1119→
  1120→  1120→### Rule 3: Verify against production after every push
  1121→  1121→After every `git push`, check the Vercel Deployments tab. If the build is red, **stop and fix it before doing anything else.** A pile of undeployed commits is a time bomb. The live site is the truth; your local build is a suggestion.
  1122→  1122→
  1123→  1123→### Rule 4: Don't build what you don't need yet (YAGNI for founders)
  1124→  1124→You don't need email if WhatsApp covers your alerts. You don't need a custom auth system if Clerk works. You don't need a vector database if Postgres full-text search handles your queries. You don't need a message queue if a cron job does the job. **Build the simplest thing that works for your next 10 users, not your imaginary 10,000.**
  1125→  1125→
  1126→  1126→### Rule 5: Provider-abstract everything you might swap
  1127→  1127→Email provider, payment provider, AI model, WhatsApp instance — all behind typed clients in `src/lib/integrations/`. Swapping is a one-file change. This is the difference between "I'm locked in" and "I can switch in an afternoon."
  1128→  1128→
  1129→  1129→### Rule 6: The dress rehearsal before the demo
  1130→  1130→Before showing anything to a real client or investor, **run the full flow end-to-end with real tools:** sign up on the live site, send a real WhatsApp message, check the live dashboard, open the proof page in an incognito window. The selftest endpoint (`/api/v1/selftest`) automates the backend check; the browser check catches what the API can't (broken buttons, wrong copy, missing pages).
  1131→  1131→
  1132→  1132→### Rule 7: Commit early, commit often, commit explicitly
  1133→  1133→After every working change, commit with a descriptive message. Stage files explicitly (`git add src/app/login/page.tsx`), not blindly (`git add .`). This prevents half-finished work or secrets from being committed. If an AI session makes a mess, you can revert to the last good commit.
  1134→  1134→
  1135→  1135→### Rule 8: The AI assistant is a junior developer, not a senior architect
  1136→  1136→AI assistants write plausible code that often has subtle bugs (wrong imports, missing null checks, incorrect API shapes, hardcoded values that should be configurable). **Review what the AI produces.** Run the tests. Check the live site. Don't trust the AI's "build passed" report without verifying it yourself. The AI is fast; you are the quality gate.

  1141→  1141→
  1142→  1142→### Testing pyramid (progressive — start small, grow as revenue justifies)
  1143→  1143→
  1144→  1144→**Day 1 (every project):**
  1145→  1145→- Playwright E2E on the critical path (sign up → log in → core feature → log out). **Run against production** (`BASE_URL=https://your-app.vercel.app`), not just localhost.

  1148→  1148→
  1149→  1149→**Week 1 (once the core flow works):**
  1150→  1150→- Unit tests on service functions (business logic) — the functions that compute money, enforce rules, or transform data.
  1151→  1151→- Integration tests on Route Handlers and webhooks (including idempotency and auth).
  1152→  1152→
  1153→  1153→**Month 1 (once you have paying clients):**
  1154→  1154→- AI eval suite for prompts/tools (golden-conversation tests, grounding accuracy, refusal correctness).
  1155→  1155→- CI gates: typecheck, lint, tests, migration check on every PR. Preview deployment per PR.
  1156→  1156→- Cross-tenant leak tests.
  1157→  1157→
  1158→  1158→**Quarter 1 (once you have 10+ clients):**
  1159→  1159→- Smoke E2E on every critical path, run in CI on every deploy.
  1160→  1160→- Observability: structured logs with request/tenant IDs, error tracking, key business metrics.
  1161→  1161→- Feature flags for risky launches; instant rollback via Vercel deployments.

  1164→  1164→```ts
  1165→  1165→// playwright.config.ts
  1166→  1166→import { defineConfig } from '@playwright/test';
  1167→  1167→

  1169→  1169→const isLocal = baseURL.includes('localhost') || baseURL.includes('127.0.0.1');

  1176→  1176→  workers: 1,

  1178→  1178→  reporter: [['list'], ['html', { outputFolder: 'playwright-report', open: 'never' }]],
  1179→  1179→  use: {

  1195→  1195→## 13. Background Processing
  1196→  1196→
  1197→  1197→Escalate only as workload proves need:
  1198→  1198→
  1199→  1199→1. **Vercel Cron Jobs** — scheduled tasks (daily RLA checks, weekly summaries, monthly certificates).
  1200→  1200→2. **Triggered Route Handlers** — fire-and-forget with persistence (webhook processing, notification sending).
  1201→  1201→3. **Render workers (free tier)** — Playwright automation (portal scraping, PDF generation, heavy compute). Wake-up cron via GitHub Actions pinging `/wake` every 10 minutes.
  1202→  1202→4. **Durable workflows** (Vercel Workflow SDK) — multi-step, resumable orchestration (onboarding sequences, multi-day audit workflows).
  1203→  1203→5. **Message queues** — only when you have genuine throughput/ordering requirements that the above can't handle.
  1204→  1204→
  1205→  1205→### Render worker standard
  1206→  1206→```
  1207→  1207→render-worker/
  1208→  1208→  package.json          # express, dotenv, playwright-core
  1209→  1209→  index.js              # /wake, /health, /api/v1/portals/* endpoints
  1210→  1210→```
  1211→  1211→- `/wake` returns `{"status":"AWAKE"}` — the GitHub Actions cron pings this every 10 minutes.
  1212→  1212→- `/health` returns service status, uptime, and capability flags.
  1213→  1213→- Portal automation endpoints use `playwright-core` with **lazy browser require** (the browser is only launched when a portal route is called, not at startup). If the browser isn't installed, the endpoint returns a structured error — **it never crashes the server.**
  1214→  1214→- The worker is a **separate package** with its own `package.json`. It is NOT part of the Next.js build. Vercel never touches it.
  1215→  1215→
  1216→  1216→### GitHub Actions wake-up cron
  1217→  1217→```yaml
  1218→  1218→# .github/workflows/keep-render-warm.yml
  1219→  1219→name: Keep Render Warm
  1220→  1220→on:
  1221→  1221→  schedule:
  1222→  1222→    - cron: '*/10 * * * *'
  1223→  1223→  workflow_dispatch: {}
  1224→  1224→jobs:
  1225→  1225→  ping:
  1226→  1226→    runs-on: ubuntu-latest
  1227→  1227→    steps:
  1228→  1228→      - name: Wake worker
  1229→  1229→        run: curl -sS -o /dev/null -w "worker=%{http_code}\n" "${{ secrets.WORKER_URL }}/wake" || true
  1230→  1230→      - name: Wake Evolution
  1231→  1231→        run: curl -sS -o /dev/null -w "evolution=%{http_code}\n" "${{ secrets.EVOLUTION_API_URL }}/" || true
  1232→  1232→```

  1246→  1246→
  1247→  1247→Start with one deployable application. When **measured** production metrics show a bottleneck (latency, cost, team contention, compliance boundary), extract **only the affected module**:
  1248→  1248→

  1257→  1257→## 16. Open-Source Integration & Architecture Preservation
  1258→  1258→
  1259→  1259→> **The application owns the architecture. The open-source project never owns the application.**
  1260→  1260→
  1261→  1261→Never restructure the application around a repository. Integrate the repository into the existing architecture (§2). The architecture is permanent; repositories are replaceable implementation details.
  1262→  1262→
  1263→  1263→### Repository evaluation framework
  1264→  1264→
  1265→  1265→| Type | Examples | Strategy |
  1266→  1266→|---|---|---|
  1267→  1267→| **1 — Utility** | Logger, date lib, PDF generator, CSV parser | Install directly. No wrapper unless it exposes business functionality. |
  1268→  1268→| **2 — Library / SDK** | AI SDK, OCR SDK, vector DB SDK | Install, then wrap behind an internal service. Never expose vendor APIs throughout the app. |
  1269→  1269→| **3 — Engine** | Recommendation, search, vision, workflow, RAG engines | Integrate through adapters behind domain services. Must remain replaceable. |
  1270→  1270→| **4 — Application** | CRM, ERP, booking system, CMS | **Never deploy as the product.** Extract valuable modules; rebuild inside your architecture. |
  1271→  1271→| **5 — Reference** | Demos, research prototypes | Study and borrow ideas. Never a production dependency. |
  1272→  1272→
  1273→  1273→### Adapter pattern (mandatory for Types 2–4)
  1274→  1274→```
  1275→  1275→Business logic → internal service → adapter (src/lib/adapters/<repo>/) → repository
  1276→  1276→```
  1277→  1277→The application owns the interface; the repository provides the implementation. Swapping engines/repos is a configuration change, not a rewrite.
  1278→  1278→
  1279→  1279→### Fork & upstream strategy
  1280→  1280→- Never ask "should I build my app inside this repository?" — ask "**which capabilities from this repository improve my app?**"
  1281→  1281→- Keep forks minimal and close to upstream. Never couple business logic to forked internals.
  1282→  1282→
  1283→  1283→### Final test
  1284→  1284→Before any integration: *"Which capability does this add to my platform?"* — never *"How do I build my platform inside this repository?"*
